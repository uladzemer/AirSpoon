# Проверка обновлений (2026-10-28)

Решения владельца: оба приложения; источник — GitHub Releases репозитория `uladzemer/AirSpoon` (публичный); при найденном обновлении — скачать и установить по кнопке; в настройках — «Проверять обновления» (по умолчанию вкл.).

Финишная черта: тесты Windows и Android зелёные; сборки с версией из тега видят более новый релиз и ставят его; при выключенной настройке запросов в сеть нет.

## Общие правила
- Источник: `GET https://api.github.com/repos/uladzemer/AirSpoon/releases/latest` (без токена). Файлы: `AirSpoonSender.exe`, `airspoon-armeabi-v7a.apk` (release, R8, подпись AirSpoon). Для клиентов 0.1.x тот же APK публикуется также как `airspoon-debug-armeabi-v7a.apk`; это совместимое имя, не debug-вариант. Проверка `size` и `digest` (`sha256:…`), если поле есть.
- Версия = тег `vX.Y.Z` (CI передаёт `AIRSPOON_VERSION`). Локальные сборки без версии сами не проверяют.
- Проверка: через ~1 мин после старта, потом раз в сутки; ошибки сети — только в журнал.

## Подписанный манифест (аудит 3.3, 2026-10-29)

Релиз содержит `airspoon-update.json` и `airspoon-update.json.sig`. Инструмент
`windows/tools/signmanifest` использует только стандартную библиотеку Go и Ed25519.
JSON в UTF-8 без BOM, пробелов и завершающего перевода строки:
`{"version":"X.Y.Z","assets":[{"name":"AirSpoonSender.exe","size":123,"sha256":"<64 lowercase hex>"},...]}`.
Порядок полей фиксирован, ассеты отсортированы по имени. Включены EXE, release-APK и его
совместимая копия `airspoon-debug-armeabi-v7a.apk`. Подпись — base64 от 64 байт Ed25519
над точными байтами JSON. Приватный ключ — base64 от 32-байтного seed, не от 64-байтного
расширенного ключа. Приватный ключ не выводится инструментом и не входит в артефакты.

Корни доверия (одна константа на платформу):

- Windows: `windows/internal/update/manifest.go`, `UpdatePublicKey`.
- Android: `android/app/src/main/kotlin/io/github/jqssun/airplay/update/UpdateSignature.kt`, `PUBLIC_KEY`.

Обе константы пока равны `REPLACE_WITH_ED25519_PUBLIC_KEY`. Обычные сборки и тесты допустимы,
но CI по тегу до сборки проверяет отсутствие заглушки, равенство ключей и длину 32 байта.
Клиенты с заглушкой отказывают в установке. Ключ нельзя получать из релиза, API или манифеста.

Клиент находит манифест и подпись по точным именам в списке файлов выбранного релиза;
отсутствие, дубликат, превышение лимита (JSON 64 КиБ, base64-подпись 256 байт), плохая подпись,
несовпадение версии с тегом или имени/размера/SHA-256 файла блокируют установку с русской
ошибкой. Сохраняются HTTPS (включая редиректы), проверки размера и GitHub digest.
Доверенный SHA-256 обязателен даже при отсутствии digest в GitHub API. Android дополнительно
сохраняет системную проверку подписи APK при обновлении через PackageInstaller.
Ed25519 на API 23+ проверяется `NativeBridge.nativeVerifyEd25519` через уже собираемый
OpenSSL 3.4.8 (`crypto` в CMake), `EVP_PKEY_ED25519` и однократный `EVP_DigestVerify`
без предварительного хеширования и без новой зависимости; см.
[документацию OpenSSL](https://docs.openssl.org/3.4/man7/EVP_SIGNATURE-ED25519/).
Версия 0.1.2 манифестов не знает: переход на первый защищённый клиент требует доверенного
первоначального обновления. Смена pinned key требует отдельного доверенного перехода.

### Граница доверия CI

Подпись защищает от подмены GitHub Releases/API/файлов, если ключ подписи недоступен
атакующему. Обычный repository secret недостаточен против аккаунта, способного менять
workflow: такой аккаунт может запустить подпись своего файла. Поэтому задание `release`
использует окружение `update-signing`; секрет `AIRSPOON_UPDATE_SIGNING_KEY` должен быть
**environment secret**, без одноимённой repository/organization-копии. Доступ к окружению
нужно защитить независимым одобрением, запретом самоодобрения и обхода защиты
администратором; одобряющий проверяет исходники workflow, коммит тега и происхождение
артефактов. См. [защиту окружений GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).
Само наличие `environment:` в YAML эту защиту не настраивает. Полный захват администратора,
который может снять правила окружения, остаётся за границей гарантии: для него нужен внешний
сервис подписи или офлайн-подпись с независимым владельцем ключа.

CI после скачивания артефактов устанавливает Go через закреплённый SHA `setup-go`,
создаёт совместимую копию APK, подписывает три файла и публикует манифест с подписью.
Ключ передаётся только в `env` шага подписи задания выпуска по тегу; пустой/неверный
ключ завершает выпуск ошибкой. В логах нет seed или его производных приватных данных.

### Действия владельца перед первым тегом

1. Из каталога `windows/` выполнить в **cmd.exe** (каталог ключа создаётся автоматически):

   ```bat
   go run ./tools/signmanifest keygen -out %USERPROFILE%\.airspoon\update-signing.key
   ```

   В stdout будет **только публичный ключ**. Seed остаётся в файле, существующий файл
   не перезаписывается. На POSIX файл создаётся с `0600`; на Windows Go не настраивает ACL
   этим режимом, поэтому ограничить доступ владельцем (PowerShell, без вывода содержимого):

   ```powershell
   $keyFile = Join-Path $env:USERPROFILE '.airspoon\update-signing.key'
   $owner = [System.Security.Principal.WindowsIdentity]::GetCurrent().Name
   icacls $keyFile /inheritance:r /grant:r "${owner}:(F)"
   ```

2. Вставить напечатанный публичный ключ в обе указанные константы вместо заглушки.
   Проверить, что строки совпадают; приватный файл не добавлять в репозиторий.
3. Создать и защитить GitHub Environment `update-signing` по правилам выше. Независимый
   reviewer должен иметь отдельный защищённый аккаунт. Разрешить только релизные теги `v*.*.*`.
   Затем из **cmd.exe**, в этом репозитории:

   ```bat
   gh secret set AIRSPOON_UPDATE_SIGNING_KEY --env update-signing < "%USERPROFILE%\.airspoon\update-signing.key"
   ```

   Команда `gh secret set AIRSPOON_UPDATE_SIGNING_KEY < файл` без `--env` создаёт repository
   secret и не обеспечивает требуемую независимость. Не хранить такую копию секрета.
4. Сделать защищённую резервную копию файла как для `release.jks`; не выводить содержимое
   ключа и не коммитить его. Потеря ключа блокирует обычный путь будущих обновлений.
5. Запустить проверки Go и Android в CI, затем выпуск по новому тегу. Проверить отказ
   при изменении JSON/подписи/EXE/APK и успешную установку на Windows и приставке.

Модульные тесты Go покрывают подпись, канонический JSON, подмену/отсутствие файлов,
версию, имя, размер, SHA-256 и HTTPS-редиректы; JVM-тесты Kotlin — разбор, выбор файлов,
сопоставление версии/имени/размера/хеша и отказ проверки подписи через подменяемый интерфейс.
JNI и установка на устройствах требуют отдельной проверки Android-сборкой.
